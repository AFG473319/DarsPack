# Known Limitations (محدودیت‌های شناخته‌شده)

Honest list of what DarsPack v0.1 does **not** do. Stating flaws openly is deliberate: honest engineering earns trust.

## Product scope

1. **Search covers names and metadata only** — not the text *inside* PDFs or Office files. Windows itself does not index PDF content by default either. Full-text search (FTS5 + Persian tokenization) is future work.
2. **Duplicates and conflicts are flagged, never resolved.** The app will not delete, merge or overwrite anything — the user decides. This is deliberate, not missing functionality.
3. **No filesystem auto-discovery.** Files enter the library only by manual import (file picker or phone upload). A watched-folder mode is future work.
4. **Filename-based metadata suggestions are heuristics.** They work on common Persian school patterns («نمونه سوال ریاضی نهم فصل 3»); unusual names get no suggestions and remain unclassified until the user edits them. There is no AI/OCR.
5. **Package verification detects, it does not repair.** A corrupt package is reported precisely but never auto-fixed.

## Platform and environment

6. **The phone client needs a running desktop "hub".** A phone-only classmate can browse/search/upload only while some PC on the Wi-Fi runs DarsPack with sharing enabled. A standalone mobile app is a v2 goal, not part of this version.
7. **The LAN share is plain HTTP on the local network — and the PIN travels in the URL.** There is no TLS: anyone who can sniff the same Wi-Fi can read the traffic. Every `/api` call, including the view/download links handed to the browser, carries the 6-digit PIN in the query string (`?pin=...`). The server silences its own request log, compares the PIN with `hmac.compare_digest`, and locks out an IP for 30 s after 5 wrong tries — but the PIN still appears in the browser's address bar and history, and inside any file link a classmate copies or shares. Treat it as a convenience gate for classmates on a trusted network, not a secret; do not reuse it anywhere else. HTTPS and a header/cookie-based session would fix both weaknesses but are not planned for v1 (a local certificate would also bring browser warnings). Mitigations (2026-11-19): the share dialog has a «رمز تازه» button that issues a fresh PIN at once (old links die immediately), and sharing stops by itself after 30 minutes — a leaked PIN now has a short life, but it is still not a secret. See also #20.
8. **School Wi-Fi may isolate clients.** If devices cannot see each other, the phone hotspot (laptop joins the phone's hotspot) is the reliable demo fallback.
9. **Windows only** for the desktop app. The web client works in any browser, but the hub is Windows (PyInstaller build).

## Engineering

10. **Search is SQL `LIKE`, not FTS.** Word order no longer matters (multi-token search: every word of the query must match somewhere), but a token also matches inside longer words («فصل یکم» contains «فصل یک»), and the note is matched as stored — typing-style differences (ي/ی، نیم‌فاصله) inside a note don't match until a `note_norm` column lands. Fine for thousands of files; a student's library of a few hundred files is nowhere near the limit, but it would not scale to tens of thousands — that is FTS5 + Persian tokenization, future work.
11. **SQLite, one writer at a time.** Concurrent imports from the desktop UI and the web server serialize with a 5-second busy timeout. For one user this is a non-issue; it is not a multi-user database.
12. **Hashing speed is CPU-bound.** Measured SHA-256 throughput on the target i5-2450M is **30–55 MB/s** in Python (a single core); a 500 MB video takes ~10–15 seconds — with a visible progress bar. An early draft of this document claimed 150–250 MB/s; the real number is lower and was corrected after a proper measurement (corrected after a proper measurement). Import reads each file twice (hash pass + copy pass); large media is the slow case.
13. **The exe is unsigned.** Windows SmartScreen shows a warning on first run ("More info → Run anyway"). Code-signing certificates cost money; the demo script covers this in one sentence.
14. **No *automatic* backups of the library.** The app has a one-click backup («پشتیبان‌گیری»): one ZIP holding the browsable package (manifest + files + index), the catalog snapshot (`catalog.db`) and a restore guide — but the user must press it; nothing schedules or runs on its own, and restoring is still the documented manual steps. The ZIP's `files/` keeps the catalog's internal names (`000001.pdf`) so that replacing `catalog.db` together with the whole `files/` folder reconstructs a working library; an earlier build stored friendly display names, so a restore left the files unreferenced and the startup sweep deleted them. Fixed 2026-11-17 with an end-to-end regression test (restore → reopen → every file still present and available). A backup made before that fix carries friendly display names instead; restoring one is still safe since the same day: the sweep's rescue pass re-homes those copies by SHA-256 on the next open (#23).
15. **The phone client's JavaScript is only lightly guarded.** pytest covers the server and a static wiring check (ids exist, script parses). Since 2026-10-29 a Node boot harness also runs the client against a stub DOM to guard which panel is visible after a reload; there is still no real-browser automated test, so real-phone testing remains manual. (A silent JS failure hid a broken PIN button until a real user tried it; a display bug later left returning visitors on a blank page.)
16. **Subject classification quality depends on filenames.** Files with unhelpful names («IMG_2026.pdf») start unclassified and rely on the user completing them via the review dialog / «بدون درس» filter. The app makes this visible rather than guessing.
17. **~~The second distinct phone upload in a share session fails~~ — FIXED (2026-10-26).** The server used to write the `web_upload` log row after the import transaction, on the request thread's own connection, and never commit it; the connection stayed alive in the server's registry, so the uncommitted write held SQLite's write lock for the whole session — the second upload with *new* content stalled ~5 s and failed. The server now commits the log row explicitly (regression tests: the row exists, and two distinct uploads in a row both land).
18. **~~Stopping the share server races an in-flight request's log write~~ — FIXED (2026-10-26).** Handler threads used to run as daemons, which `ThreadingMixIn` never tracks or joins, so `stop()` closed each request thread's SQLite connection while a request could still be inside its log write (a native access violation). Handler threads are now joinable, so `server_close()` waits for them before any connection is closed. The test suite's own workaround (`daemon_threads = False`) became the product fix.
19. **The test suite can exit non-zero even when every test passes (Qt offscreen teardown crash).** On this machine some Qt widget tests (notably `tests/test_classify.py`) occasionally crash the pytest process during interpreter shutdown — exit code 127 or 139 — after the summary line reports all tests passed. Reproduced on a clean checkout of the same commit, so it predates the 2026-10-29 icon work and is not caused by any app code; the tests themselves pass. On this machine treat the green summary line as the pass signal, and re-run any file that exits non-zero to confirm. Not yet fixed.
20. **The phone web app is installable only as far as the browser allows over plain HTTP.** The client ships a manifest and 192/512 px icons, but Chrome requires a secure context (HTTPS or localhost) for a full PWA install and service-worker features. On the LAN address (`http://192.168.x.x`) Android may offer «افزودن به صفحهٔ خانه» as a shortcut rather than an installed PWA. Adding HTTPS with a local certificate would add browser warnings; not planned for v1.

21. **The rounded-popup fix is applied by monkey-patching Qt classes (accepted trade-off, 2026-11-10).** Qt's Fusion style draws an opaque square container behind the rounded `QComboBox` popup and `QMenu` corners. `ui/theme.py` fixes it in two ways: a `combobox-popup: 0` / transparent `QComboBoxPrivateContainer` QSS rule, and `setup_combobox()`, which gives the popup container a translucent attribute plus frameless popup flags. To reach every combo and menu created anywhere in the app (row menus and filter menus are built on the fly), `setup_combobox()` is wired in by replacing `QComboBox.__init__`, `QComboBox.setView` and `QMenu.__init__` at import time. This works and is covered by tests, but it is the one place in the codebase that changes Qt classes process-wide, which makes it harder to explain to a reader and couples us to Qt internals. The honest alternative - calling the helper at each of the 16 construction sites - was rejected only because new menus are still created later at runtime and would be missed. If this ever causes trouble with another widget, delete the three `_patched_*` blocks and call `theme.setup_combobox(combo)` explicitly where needed; nothing else depends on the patching.

22. **The MCP server is a second process, not a second window (2026-11-14).** AI agents start `DarsPackMcp.exe` over stdio; it shares the library with the desktop app through SQLite WAL. Consequences worth admitting: (a) a classification made by an agent is on disk immediately but the open GUI table only shows it after `F5`, because there is no cross-process push; (b) each connected client spawns its own ~32 MB process — three clients mean three processes reading the same catalog; (c) the server needs the frozen build's headless exe. A source checkout works through `PYTHONPATH` (the generated config includes it), but a *partially copied* `dist` folder that lacks `DarsPackMcp.exe` fails, and the Help Center then shows a warning instead of a command that would only reopen the GUI. (d) `_resolve_library_path()` can only read `settings.json` from the default library folder; generated configs always pass `--library` explicitly, so this only affects hand-written configs.

23. **Startup reconciliation deletes unreferenced files in `files/`.** `Library.open()` calls `sweep_orphans()`, which removes `tmp_*` leftovers **and any top-level file whose name is not in the catalog's `stored_name`** (a row whose import rolled back). It never touches the `.trash/` subfolder. This is deliberate crash recovery, but it means `files/` is a DarsPack-managed folder: do not keep unrelated personal files there, and always restore a backup by replacing `catalog.db` *and* the whole `files/` folder together. This is the mechanism that turned the old, mis-named backup into data loss (#14); the backup now names its members to match the catalog. Since 2026-11-17 (same day) the sweep first runs a **rescue pass**: an unreferenced file whose SHA-256 matches a catalog row that has lost its own file is *renamed* into that row's stored name instead of being deleted (logged as `rescue`), so even a backup made before the fix is safe to restore — anything matching no waiting row is still swept.

## Bugs found and fixed in real use

Each was reported in real use via the in-app crash dialog, fixed, and covered by a regression test:

1. Import hung on «در حال وارد کردن» — one failing file killed the worker thread before the completion signal (silent in a windowed exe). Fixed: per-file error containment, guaranteed `done`, `error.log`, global crash dialog.
2. The metadata dialog crashed on files without a subject (missing `subject_name` column in its query). Fixed: JOIN subjects.
3. The phone PIN button did nothing (client JS referenced a non-existent implicit global). Fixed: explicit element lookups + inline errors + static wiring guards.
4. The feedback button crashed (Qt passes `checked` to plain-function slots). Fixed: lambda wiring + a wiring-guard test.
5. **The phone client showed a blank page on every reload with a saved PIN** (found during the 2026-10-29 UI audit). The library rows were rendered, but both panels stayed `display:none`; only the first PIN entry ever un-hid the list. Fixed: the list is shown whenever a stored PIN exists (a stale PIN falls back to the PIN screen); guarded by a Node boot test and verified in a real browser.
6. **The welcome text sat left of center on first open** (reported in real use, 2026-10-29). It was centered against the table viewport before the first layout had final geometry. Fixed: the viewport's resize event re-centers the overlay; regression test pins the centered position on first show.
